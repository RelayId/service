How RelayId works

RelayId is a device-backed identity bridge. It connects an upstream account provider, a RelayId client, and a downstream OIDC application without handing the downstream application a device secret.

Three protocol boundaries

RelayId keeps the system understandable by separating three jobs:

  1. Upstream OAuth2: RelayId sends the person to a configured provider such as Google, then receives the provider callback and verified identity.
  2. Relay device API: the client enrolls a device, polls or receives login state, and signs approvals with its device credential.
  3. Downstream OIDC: an application such as Cloudflare Access treats RelayId as its OpenID Connect provider and receives tokens from RelayId.

The upstream provider and downstream OIDC client are different configuration objects. The downstream application never uses the upstream provider credentials.

Device enrollment

  1. The client creates an enrollment

    The RelayId client sends its public device information to POST /api/enrollments. RelayId returns a short-lived enrollment identifier and browser URL.

  2. The user opens the browser URL

    The browser reaches /enroll/{id}. RelayId shows only the upstream providers configured for that enrollment.

  3. The user verifies an upstream account

    The browser starts /oauth2/{provider}. RelayId owns state, PKCE, callback validation, and the short-lived transaction. It does not persist the upstream access token.

  4. RelayId binds the identity

    RelayId requires a stable upstream subject and usable verified email evidence, then stores the provider namespace and subject as the stable identity binding.

  5. The device completes enrollment

    The client polls GET /api/enrollments/{id} and completes the enrollment with the signed device request. The resulting device credential is returned only to the client.

OIDC sign-in

  1. The application starts authorization

    The relying party redirects the browser to /oidc/authorize with its client ID, exact redirect URI, state, and a PKCE S256 challenge.

  2. RelayId creates a browser login

    RelayId displays a QR code and a short mobile code. The browser transaction is single-use, short-lived, and bound to its browser cookie.

  3. The client approves the login

    The RelayId app reads the pending login through the device API and submits a signed approval. RelayId verifies the device credential, device signature, expiry, replay protection, and login binding.

  4. The application exchanges the code

    The browser is redirected back to the application with a one-time authorization code. The application sends that code and its PKCE verifier to /oidc/token.

  5. RelayId issues OIDC tokens

    The application validates the returned ID token using the public keys at /oidc/jwks. Discovery is available at /.well-known/openid-configuration; UserInfo is available at /oidc/userinfo.

Configuration model

RelayId has two independent provider lists:

  • oauth2.providers contains upstream account providers used during enrollment.
  • oidc.clients contains downstream applications that are allowed to trust RelayId.

The public issuer must be the permanent HTTPS origin users and relying parties can reach. The container only needs a local listen port; TLS belongs at the public proxy or tunnel.

Operational endpoints

Use GET /api/status for readiness and bounded runtime statistics, GET /api/providers to see configured upstream providers, and GET /.well-known/openid-configuration to inspect the downstream OIDC contract.

Keep the YAML configuration and signing keys outside the application image. Mount the configuration read-only and mount the OIDC and device signing keys from the secrets directory.
