How RelayId works

RelayId is a device-backed identity bridge connecting an upstream account provider, a RelayId client, and a downstream OIDC application.

Three protocol boundaries

RelayId separates account verification, device communication, and downstream sign-in.

  1. 1. Upstream OAuth2: RelayId receives a verified identity from a configured provider.
  2. 2. Relay device API: the client enrolls a device, receives login state, and signs approvals.
  3. 3. Downstream OIDC: an application trusts RelayId and receives tokens.

Device enrollment

  1. 1. The client creates an enrollment

    The client sends public device information to POST /api/enrollments and receives a short-lived browser URL.

  2. 2. The user verifies an account

    The browser starts /oauth2/{provider}; RelayId owns state, PKCE, callback validation, and the short-lived transaction.

  3. 3. The device completes enrollment

    The client polls GET /api/enrollments/{id} and completes enrollment with its signed device request.

OIDC sign-in

  1. 1. The application starts authorization

    The relying party redirects to /oidc/authorize with its client ID, redirect URI, state, and PKCE challenge.

  2. 2. RelayId creates a browser login

    RelayId displays a QR code and optional short mobile code in a single-use browser transaction.

  3. 3. The client approves the login

    The app submits a signed approval; RelayId verifies the credential, signature, expiry, replay protection, and browser binding.

  4. 4. The application exchanges the code

    The application sends the one-time authorization code and PKCE verifier to /oidc/token.

Configuration model

oauth2.providers contains upstream account providers. oidc.clients contains downstream applications allowed to trust RelayId. The public issuer is the permanent HTTPS origin.

Operational endpoints

Use GET /api/status for readiness, GET /api/providers for configured providers, and GET /.well-known/openid-configuration for OIDC discovery.
